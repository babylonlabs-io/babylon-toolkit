# Vault wallet requirements audit

- Tracks [#2447](https://github.com/babylonlabs-io/babylon-toolkit/issues/2447), part of [#2228](https://github.com/babylonlabs-io/babylon-toolkit/issues/2228).
- Source revision: `8f62bcfa` on `main`.
- Vault still requires BTC and ETH wallets. The connector can make a chain optional, but Vault does not use that option.
- This audit records current behavior. It does not approve a new wallet policy or change application behavior.

## Connection checks

## Prompts, restore, and disconnect

- Vault has no shared action-specific BTC connection helper. A missing wallet normally produces a connect state, unavailable action, or error. The epic requires a separate explicit action after BTC connects. Connection must never run the pending action.
- Selecting wallets is distinct from confirming the dialog. `Connect` checks confirmation, but `useConnection` and `RootLayout` do not. Their current results can disagree before confirmation.
- `WalletProvider` uses persistent storage. The connector owns confirmation receipts and restore checks. Vault still requires both chains for that session. See [useWalletConnectors](../../packages/babylon-wallet-connector/src/hooks/useWalletConnectors.tsx) and [confirmationReceipt](../../packages/babylon-wallet-connector/src/core/confirmationReceipt.ts).
- A BTC disconnect before the first successful BTC connection does not reset the whole session. After a successful connection, a BTC disconnect starts a three-second timer. BTC reconnection cancels it. Otherwise Vault disconnects all wallets.
- A BTC address change resets all wallets immediately. An ETH address change also resets all wallets. An ETH disconnect resets all wallets outside the connection dialog. Inside the dialog, Vault suppresses the extra reset.
- Deposit resume views can start wallet work when they mount. WOTS and payout cancellation records affect this behavior. A future BTC connection prompt must preserve those records. It must not mount an auto-starting action until the user explicitly starts that action. See [ResumeDepositContent](../../services/vault/src/components/simple/ResumeDepositContent.tsx).
- Pending and expired records can exist without BTC, but some visibility flags and provider status reads still require BTC. Replacing the page connection check alone is insufficient.

## Load boundaries

- [main.tsx](../../services/vault/src/main.tsx) imports Bitcoin curve support and `bitcoinjs-lib`. It initializes curve support before the application renders.
- [wagmi.ts](../../services/vault/src/config/wagmi.ts) imports the full wallet connector entry. [VaultWalletConnectionProvider](../../services/vault/src/context/wallet/VaultWalletConnectionProvider.tsx) also imports that entry and configures both chains.
- Read paths still use broad SDK entries. Examples include [sdk-readers](../../services/vault/src/clients/eth-contract/sdk-readers.ts), [useBtcPublicKey](../../services/vault/src/hooks/useBtcPublicKey.ts), and [usePegoutPolling](../../services/vault/src/hooks/usePegoutPolling.ts).
- The merged lazy WASM loader does not prove that the Vault startup path excludes all Bitcoin code. Runtime import and browser checks belong to the later implementation and verification tasks.

## Checks needed for later behavior changes

- Exercise absent wallets, ETH only, BTC only, both wallets, and both providers connected before dialog confirmation. Test the real connection hook and the menu separately.
- Show all account pages with a confirmed ETH-only session. Verify borrow, repay, collateral withdrawal, and vault reorder without a BTC prompt.
- Restore an ETH session when BTC is absent, late, locked, or rejected. Disconnect or switch BTC without silently dropping ETH. Check ETH disconnect and account changes separately.
- Open each BTC action from an ETH-only session. Check cancel, connection failure, wrong BTC account, and retry. Connection must run no pending action. Require a separate explicit action after connection. Preserve deposit and cancellation state.
- Keep pending, expired, and withdrawal records visible. Distinguish status reads from signing authority. Check account changes and stale results.
- Check activation, emergency withdrawal, and artifact authentication with the exact wallet requirements in the action table. A cached token must not be mistaken for general wallet independence.
- Run browser checks for ETH-only entry, deferred Bitcoin loading, and the existing two-wallet staking consumer after the behavior and package changes land.

## Open decisions and dependencies

- [#2230](https://github.com/babylonlabs-io/babylon-toolkit/issues/2230) and [#2231](https://github.com/babylonlabs-io/babylon-toolkit/issues/2231) remain dependencies for the Vault behavior change. This audit can proceed before them.
- Define when ETH-first access requires explicit dialog confirmation. The current menu and page checks differ. Do not copy one rule to the other without this decision.
- Define whether activation must continue to recover a secret through BTC or also offer manual secret entry. An ETH-only handler is not a product decision.
- Define whether adding or replacing optional BTC requires a new confirmation receipt. Preserve the confirmed ETH identity during cancel, failure, and restore.
- Define which source supplies BTC identity for status reads when BTC is absent. Keep the signing ownership checks at the action boundary.
- The earlier `feat/vault-optional-btc-wallet` work was closed without delivery. Its code is reference material. It is not evidence that the behavior is present in `main`.
